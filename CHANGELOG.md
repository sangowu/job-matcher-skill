# Changelog

All notable changes to this project are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Changed
- `HttpAtsProvider` can post. It was documented as GET only, and that was worth something: a GET cannot be mistaken for a write. Workday's search endpoint answers 400 to GET on the bare path and to every query-string spelling of the same arguments, so reaching it at all means posting the search. What is posted is built in `ats_provider` from a page offset and a limit -- no caller supplies it, nothing from a CV or a profile enters it, and `searchText` stays empty for the same reason `amazon_jobs_url` takes no query. The verb is the endpoint's requirement, not a change of intent, and the widening is recorded as one.
- A market no longer owns the sources a round reaches. A structured board is fetched in one request that returns the whole board, every country in it -- and the catalog decided, before the request, which markets that board was allowed to serve. Its reading was routinely short: across the 59 boards an ie round now plans, 10,264 postings, 2,579 of them in countries no market covers, all fetched and dropped before anything could read them. `build_source_plan` now plans a structured source for every market the round asked for whatever it declares, and each posting's own location decides afterwards in `filter_to_markets`; a source the structured channel cannot reach is still filtered, since it is queried per market in that market's own language. For ie itself this is +32 postings (+5.8%), which is what a market with 38 curated sources had left to gain -- the change is for the markets that do not exist yet, where the Netherlands is already 147 postings in hand. Two further gates on the same fact went with it: `markets.json` held a per-market `source_ids` mirror of what each source declares, 171 entries, checked for equality and separately fed to `discovery_plan`, and it is the mirror that broke first -- failing validation for one file on a one-word edit to the other. Both validators now refuse the key rather than ignoring it, so it cannot come back a row at a time, and `seed_promotion` no longer performs text surgery on a second hand-written file to keep it in step. An ie round goes from 23 structured boards to 59; boards naming the round's market sort first, so a tight `ats_boards_per_round` still buys the boards the round already had. Evidence in `docs/performance/market-source-decoupling-2026-09-28.json`.
- The report has one path. Every round wrote a whole new `report_<timestamp>.html` with its data baked in, so the link changed each time and nothing could be bookmarked -- eighteen files and 3.3 MB had accumulated on the machine this was measured on, with no way to tell which was current except the name. The page is now `data/reports/report.html`, a verbatim copy of the template carrying no data at all, and the round rewrites `report_data.js` beside it; the page is touched only when the template itself changed, so a tab left open is still the right tab and a reload shows the new round. The data is JavaScript rather than JSON because the page is opened as a `file://` URL, where `fetch` of a sibling file is blocked by the opaque origin and a script tag is not -- both measured in a browser before the change, along with the reload picking up a rewritten data file without any cache-busting. `render_html.py` now also returns `report_data_path`. Old timestamped reports are left where they are.
- The report's market filter had four labels, so a us row rendered as the raw key `market_us` -- the same hand-kept market list the envelope schema had, found by opening the page. A test now requires a label in both languages for every market in the catalog.
- jobs.ie is open to the browser channel, on what its robots.txt actually says. All four ie sources carrying `automation_allowed: false` were re-checked with `check_robots.py` against the URL a round would really visit, query string included. Three were confirmed by the site's own published rules and left alone: LinkedIn refuses the whole host (`disallow: /`) and needs a signed-in account besides; Indeed allows the listing and refuses `/viewjob`, which is where the JD is; Accenture allows its landing page and refuses `*/careers/jobsearch?`, exactly as the recorded constraint said. jobs.ie asserts nothing about any of its paths, and its entry page shows 3,448 public jobs with no login and no bot interstitial -- while the same market's other local job board was already automation_allowed on the same footing, so the two were inconsistent with nothing behind the difference. Evidence in `docs/performance/jobs-ie-automation-recheck-2026-09-28.json`. jobs.ac.uk carries the same constraint, was not re-checked, and keeps it. Three tests named `jobs-ie` as their example of a refused source and broke on the curation: two of them are about the rule, not the source, and now take a refused ie source from the catalog instead.

### Fixed
- `multi_region_smoke.py` recognises Dutch job links. It matched them by an English stem list that had already been given German's `stelle`, and `vacature` shares no substring with `vacanc` -- so every Dutch job link read as navigation and the market observed zero candidates while reporting the run as successful. Found by adding a market, not by reading the list.
- The per-market company/ATS minimum is gone. It required ten verified company, ATS or global-board sources naming each market, which counted the catalog rows written for a market rather than what the market could reach -- and the two had come apart: cn carries fourteen curated sources and 11 postings, nl carried none and 146. A structured source is now planned for every market or none, so what is left to require is that the catalog has that channel at all, which is now a single catalog-wide minimum. The per-market minimum of three local sources stays: those are queried per market in that market's own language.
- The market list in `README.md` and `WORKFLOW.md` no longer names a count. They said four markets in one place and five in another, both stale, three weeks after the fifth was added. The catalog is the authority and the docs now point at it.
- A posting in two markets is attributed to both, instead of to none. The job table's field is `market_ids`, plural, but provenance carried only a singular `market_id`, and `ats_pipeline` set it to `null` whenever a location resolved to more than one market -- on the reasoning that several markets is a guess. It is not a guess: "Dublin, Ireland; London, England" is two markets and the catalog is certain about both, so the row landed with `market_ids: []` and `market_status: "unknown"`, which the report can neither filter nor place. Measured on the live table, eight of eighty-five rows. The envelope now carries `market_ids` alongside `market_id`; the singular field keeps its meaning -- exactly one market or nothing to say, which is what a task scope check reads -- and the contract refuses a singular value absent from the plural list, an unknown-confidence location asserting either, and more entries than there are markets. `merge_jobs` reads the plural field and falls back to the singular one, and a source re-reported with a placement fills one the stored copy never had, the lazy migration the rest of the table already does; a placement that exists is never overwritten. The published schema also still listed four markets, three weeks after a fifth was added, because the guard comparing it to the runtime constants covered `discovery_route` and `source_type` and not this enum -- it covers all three now.
- A role family the CV already targets is no longer reported as a generalization of it. The backend family generalizes to applied_ai, so a CV naming both an AI role and a Python backend role had `Applied AI Engineer` returned in `generalized_roles` -- a title `target_roles` already held. Downstream dedupe meant nothing was searched twice, so the visible cost was a plan claiming a widening it had not made; the real cost was inside `_variants_for_role`, where the duplicate still spent one of the role's three variant slots on a title another target role was already contributing. The occupied families are now excluded before the cap rather than after, so the slot goes to a family the CV has not reached yet: on the live profile, `generalized_roles` went from three titles (one of them already targeted) to two that are new, and the same six-call budget bought five distinct queries per market instead of three.
- `tests/test_market_plan.py` inserts `tools/` on the path itself. Moving `multi_region_smoke.py` out of `scripts/` left its import here reachable only once `test_multi_region_smoke.py` had run, so the file passed in the suite and failed when run alone.

### Added
- Workday, a fourth ATS provider, and five boards on it. One code path reaches many tenants: every Workday-hosted careers site answers the same URL shape with the same JSON, and the five boards added here return 999 postings between them -- eBay, NVIDIA, Salesforce, Workday and Adobe, each fetched through the adapter that will fetch it in a round rather than probed by hand, with every `markets` list in the catalog measured rather than guessed. cn gains a structured channel for the first time: its fourteen curated sources are browser and Web Search only, and `per_market.cn.structured` read `unavailable_in_market` until now. A board is identified by three things, none of them droppable or derivable -- no site segment answers 400, the wrong data centre answers 422, and the bare tenant host does not resolve -- so a seed carries a new `site` field beside `board_token` and `instance`. Pushing the endpoint found four things that fail silently, each now pinned by a test: an offset past the end returns the first page again rather than an empty one (offset 2000 and 4000 on a board of 2,000 both gave offset 0's twenty rows, so pagination is bounded by `total` and a short page is only a fallback); `total` is reported on the first page only and reads 0 after it; a listing row can carry `bulletFields` and nothing else; and the page is capped at 20 where 50 is a 400. Descriptions are not in the listing at any setting, so Workday joins `CONTENT_DEFERRABLE_PROVIDERS` for the opposite reason to Greenhouse -- it cannot include them rather than can leave them out -- and `fetch_job_content` now reads a provider's own id shape and description field instead of Greenhouse's. Known limit: with a 20-row page and `ats_max_pages` bounded at 10, a board yields at most 200 postings a round, which is not arbitrary -- the default sort is newest first, so those are the 200 most recent. Runtime discovery is not included: `extract_board` returns two identifiers and Workday needs three. Evidence in `docs/performance/workday-provider-2026-09-28.json`.
- The Netherlands, the sixth market. It cost no sources on the board side: 146 Dutch postings were already being fetched and discarded, from 14 boards, none of which declares nl -- the largest contributor is Adyen's board, 58 Amsterdam postings under a catalog entry reading `[uk, de]`. That is what the market/source decoupling above was for, and this is the first market added since. Four Dutch sources are added for the browser and Web Search channels, which are market-scoped and would otherwise have nothing: Jobbird (71,162 vacancies) and Intermediair as local boards, Werken voor Nederland (1,500) and AcademicTransfer as public sector portals, each checked twice -- `check_robots.py` against the search path with its query string, then a fetch of the entry page to see a listing is served there. Six more were examined and left out, with the reason recorded: nationalevacaturebank refuses `/vacature/zoeken?*`, nl.indeed refuses `/viewjob` exactly as the Irish host does, magnet.me serves 11 KB with no listing in it, techleap 404s, werk.nl answers a redirect nobody followed, and monsterboard's robots.txt is unreadable. The search language is English only: `default_search_languages` has to come from the internal set (en, de, zh-Hans), so Dutch would mean Dutch titles and synonyms for every role family and Dutch names for every city in every market -- a translation job rather than a market, and one the structured channel does not need since it fetches whole boards and reads locations off them. Evidence in `docs/performance/netherlands-market-2026-09-28.json`.
- `merge_jobs.py verify` records link liveness on its own, without an evaluation result. `verified` was writable only inside one, and an evaluation snapshot accepts a result exactly once by design -- so a round that checks links outside the scoring worker had nowhere to put the answer: measured on a live round, fifteen postings verified `alive` and the table kept `verified: null`, so the report called them unverified. Liveness belongs to the row. The command moves only `verified` and `verified_at`: it refuses a payload carrying a score, it cannot create a row (an unknown `record_id` is reported in `unknown_records` rather than invented), `null` writes nothing, since dating a check nobody made is worse than having no date, and `closed` is written down rather than acted on -- what to drop is the reading round's decision.

- A United States market, which is the first market added since the catalog was written and the proof that adding one is now catalog work. `markets.json` carries `us` with six cities and the fifty states plus DC as its own `administrative_areas`; `source_seeds.json` carries nineteen us sources. Every one was checked before it was written: fourteen public Greenhouse boards fetched through the production provider (5,149 postings, 2,050 of them in the US), and five local sources checked with `check_robots.py` against the URL actually visited, query included. Boards that did not answer, or answered with no postings, were counted and not stored; `simplyhired.com` answers 403 for its own `robots.txt`, which is not permission, so it is out; `dice.com` refuses every search and allows only the landing page, so it is seeded the way Accenture is -- `automation_allowed: false`, no direct access method, the two human paths intact. Five of the fourteen boards were already in the catalog for ie/uk/de, so the market joined their `markets` list rather than creating a second seed for the same company. Evidence in `docs/performance/us-market-seed-verification-2026-09-27.json`. The seed pool came from the request to use S&P 500 companies; index membership is not machine-checkable here and is deliberately not asserted anywhere in the catalog.

- An administrative area now says which market it belongs to, instead of only saying "not ours". `foreign_administrative_areas` was a closed reverse catalog -- fifty states, thirteen provinces, DC -- and it existed because `Dublin, OH`, `Dublin, CA`, `Berlin, CT` and `London, ON` every one resolved to Ireland, Germany or the United Kingdom with `confidence: exact`. Adding a US market makes fifty-one of those entries that market's own: Ohio stops being somewhere else and becomes a place a round can be scoped to, while the thirteen Canadian provinces stay foreign because no market covers Canada. The qualifier now *restricts* rather than short-circuits, which is what keeps `Seattle, WA` a city while `Dublin, OH` becomes the market without one -- the Irish city that matched is not in the market the qualifier names. Corroboration is read per market for the same reason: `Dublin, Ohio, United States` names by country the very market the qualifier already named, and the old yes-or-no reading handed the posting back to the Irish city alias; only a *different* market in the text stands the qualifier down, which is still what settles `Berlin, DE` as Germany over Delaware. A catalog where two markets claim one area, or a market and the foreign list claim it at once, is refused at load: two answers would be decided by iteration order.

- The nine scripts a round never runs live in `tools/` now: five benchmarks, the two shadow-gate scripts, the multi-region smoke and the first-contact browser smoke. `scripts/` was 19,900 lines and reading it gave no way to tell the 13,700 a round depends on from the 4,300 that run when a parser changes or a version ships. Each tool keeps importing the production modules through `tools/_bootstrap.py` -- that is the point, since a benchmark measuring a copy of the parser would measure the copy -- and `python tools/<name>.py` is the new invocation everywhere it was documented. The guards moved with them rather than being left behind on a smaller set: the stdin scans, the unescaped-JSON scan and the README listing all read both directories, so a tool that hangs on a missing EOF or ships undocumented still fails CI, and `ruff` now lints `tools` too.


- A posting the prefilter refuses now leaves a mark, and `candidates_dropped_repeat` says how much of a round's refusing was ground already covered. A refusal used to leave nothing but a count by reason, so a round that rediscovered the same postings and refused them again was indistinguishable from one that refused new ones -- and that difference is the answer to "the browser channel spent minutes and produced nothing", since it rereads a site's listing every round. `rejected_log.py` keeps url keys, one of four low-cardinality reasons, and timestamps under `data/rejected.json`, with the same TTL as the JD cache; no title, company, JD, CV or query. **It is a marker, never a skip**: a posting refused on `role` is refused by that profile, not forever, and the round after a CV gains a generalized role has to reconsider it -- a store consulted as a cache would keep the old answer and silently undo the generalization. So the prefilter runs on every candidate every round and this store changes only the count, which a test pins. It also saves no tokens and is not meant to: a refused candidate never reached the merge, and the worker had already paid to report it. The cost that remains is the worker rereading the listing, which needs per-source pagination memory in the task, not a negative cache.

- The rules a round follows and the reasons they are shaped that way are now two files, because only one of them has to be read every round. `SKILL.md` + `WORKFLOW.md` are loaded whatever the round finds, so their size is a fixed cost per run: 39,593 and 4,040 characters, about 18,000 tokens, before any job was searched. Much of it was reasoning -- 20 "实测" passages, 16 dated post-mortems, the argument for each constraint -- which a reader needs when changing a rule and not when following one. `WORKFLOW.md` now states the rules with a stable id each (`[R4-01]`), `docs/rationale.md` carries the same ids with the original text of the reasoning moved verbatim, and the per-round cost is about 10,300 tokens (-43%). Four more docs took what does not belong in a per-round prompt at all: `docs/ats-protocol.md` (rules governing what `ats_pipeline.py` does, not what the agent does), `docs/remote-browser-protocol.md` (off by default), `docs/phase-c-legacy.md` (superseded entry point) and `docs/shadow-and-smoke.md` (run only when asked). `SKILL.md` dropped twenty bullets that restated WORKFLOW rules and keeps only what is specific to this runtime -- both files were loaded together, so the duplication was paid twice. Two tests hold the split: every cited id must have its reasoning and every explained id must be cited, and the two per-round files have a character ceiling, so the explanations cannot creep back in.

- `references/markets.json` is now the only place the market set is written down, and a plan says per market why each channel is or is not in it. Five modules each carried their own `SUPPORTED_MARKETS` tuple and `market_plan` additionally asserted the file matched it exactly -- "markets.json must define ie, uk, cn, and de exactly once" -- so the catalog was never the answer, it only had to agree with one, and adding a market meant editing six constants and their tests before the entry counted. `_jobutil.supported_markets()` reads the catalog once and every module derives from it; the assertion is now that the file names at least one market. Verified by adding a US market to the two JSON catalogs and nothing else: `market_plan`, `source_registry` and `discovery_plan` all planned it, producing New York queries and eight browser tasks, with no Python edited. The remaining barriers are the catalog's own content rules -- three verified local sources and ten company/ATS/global ones per market -- which is curation, not code.

- A plan's `per_market` reports each channel as `planned`, `route_off`, `deferred` or `unavailable_in_market`, and a market with no planned channel at all is named in `warnings`. China skips the ATS channel and always did, correctly, since none of its fourteen sources is an `ats_board` -- but that was a side effect of the data: the plan said only that no structured task existed, with no market attached, so "this market has no structured channel" and "the wave budget did not reach it" arrived as the same silence, and a market that returned nothing looked like a market where nothing was posted. The verdicts are derived from the same catalog the tasks are built from rather than from a second hand-kept list, and `market_coverage[].channels` carries them into the report, where a card can now say the channel does not apply here.

- A CV role is now generalized to the adjacent roles its own stack supports. `references/role_taxonomy.json` carries `generalizes_to` edges, each gated by the skills the target family actually hires for, so two CVs that both say "AI Engineer" are not searched the same way: one with Python, FastAPI and PostgreSQL is also searched as Backend Engineer, one with Figma and Illustrator is not. Three titles per role, market and language is the ceiling, and each generalization costs an own-family variant slot but never the first one -- the answer to what this CV is may not be crowded out by what else it could be. The matched titles are reported as `generalized_roles` and `market_plan.py effective-profile` folds them into `roles`, because a round that searches for Backend Engineer and then filters on "AI Engineer" alone drops every generalized result on `role`, which is the searches paying for a widening the filter never heard about. `frontend` and `fullstack` families were added: `Full Stack Engineer` resolved to no family at all, so it was expanded to nothing and a Chinese market was searched for the English spelling instead of 全栈工程师.

- `market_plan.py plan` now returns `role_plan`, the full localized expansion, alongside `search_plan`, the slice of it the Web Search budget can pay for. One budget used to cut the list every channel then read: `max_websearch_calls` is six, the browser channel spends none of it, and a three-market round therefore arrived at exactly one title per role on every site it opened, with the second and third variants `_query_candidates` had already built discarded. `discovery_plan.py` builds browser tasks from `role_plan` and Web Search tasks from `search_plan`; a market plan from before `role_plan` existed falls back to `search_plan` for both, which is what that round already did. The rows are deliberately narrower than a search row -- market, language, role, location -- since the query string and template belong to Web Search and copying them would hand the orchestrator a second copy of every row it already has.

- `claude-fable-5-1` is in `references/model_tiers.json`, at the `deep` tier. It is a model this runtime offers as a subagent, and the catalog did not carry it, so it resolved to nothing and was reported in `unresolved_models` -- correct behaviour for a name nobody registered, and a gap when the runtime really does offer it. At `deep` it changes no existing selection: no role's floor is `deep`, and the cheapest-that-reaches rule keeps `search` on Haiku and `evaluation` on Sonnet. A test now pins that every model this runtime offers resolves.

- A link check now records when it happened, and a fresh one is not asked for again. Nothing stored a timestamp, so `verified` answered "is this link alive" without answering "as of when": every round re-checked the whole Top-N -- twenty-odd URLs, each with a ten-second timeout ceiling -- and a month-old `alive` was displayed exactly like one made a minute ago. `merge_jobs.py` stamps `verified_at` on every non-null result, `_brief` carries `verified` / `verified_at` / `needs_verification`, and the decision is made in Python rather than left as a rule the caller has to remember. `verify_ttl_hours` (24) is how long a check stands; only `alive` is reusable, since `closed` removes the row and the three undecided states are what a re-check exists to resolve. A worker reporting `null` leaves both the verdict and the stamp alone -- nothing was learned, which is not the same as a check that came back undecided -- and a changed JD body clears the stamp along with the verdict it belongs to. Reused checks are counted as `verification_reused`.

- A subagent profile names the tier it needs instead of a model id, and the model is chosen from what the calling runtime reports it can run. Which models exist is a fact about the runtime this skill is invoked from, and no Python here can observe it -- only the agent knows. The shipped ids named one runtime's models, so on the other the request could never be honoured: `fallback_used` was true for 64% of subagent runs to 2026-09-26, `model_effective` was reported as `unknown` for one role, and the profile mechanism was in practice inert. `config.json` now carries `min_tier` per role and `subagent_metrics.py profile --role R --available-models a,b,c` returns the cheapest model in `references/model_tiers.json` that reaches that floor. The floor is per role on purpose: an evaluation worker returns a structure `analysis_contract` validates strictly, and running that as cheaply as a search worker is how `rejected_rate` gets worse rather than how cost gets better. A name the catalog does not carry is listed in `unresolved_models` rather than placed by its spelling -- a new model whose name resembles a known one is a guess, and asking the runtime what it has exists to stop guessing -- and it costs the run nothing, since the other candidates still resolve. `model_source` says where the answer came from: `catalog`, `config` (an explicit `model` still pins one, which is the escape hatch for a runtime this catalog has never seen and is how every profile behaved before), `unresolved` (nothing offered reaches the floor) or `runtime_inherited` (no runtime reported). The last two return a null model and the runtime's current one stands, which is what already happened -- except that it is now stated rather than discovered by the request failing. `model_requested` is nullable in the metrics for the same reason: asking for nothing in particular is a real request, and recording it as an absent field would make it indistinguishable from a caller that forgot to say.

- A round that was interrupted can now be recorded as abandoned, which nothing could say before. The metrics vocabulary had `run_start` and `run_finish` and nothing else, so a round that stopped left its `run_start` dangling: counted as `stale_unfinished` once past `unfinished_run_age_minutes_max`, and pinning `metrics_status` to `incomplete` until it aged out of the window. Two of the eleven runs started in the week of 2026-09-26 were interruptions, so the completeness signal read `incomplete` for days over rounds nobody could close -- and `finish` could not close them even in principle, because it requires the round marker under `data/rounds/` and an interrupted round is exactly the case where the marker is gone. `round_timer.py abandon --round-id R --reason ...` writes a `run_abandoned` event instead. It never writes `complete`, so an abandoned round claims no coverage; it refuses a round with no `run_start`, one already finished and one already abandoned, since each would record something that did not happen; and `reason` is a closed set rather than free text, because a category field in the metrics has to stay low-cardinality. `unknown` is in that set on purpose: an abandonment whose cause nobody wrote down is still worth stating, because the fact the signal needs is that the round will never report. The count is surfaced as `runs.abandoned` and on its own line in the health report -- a round that produced nothing stays visible rather than being quietly excused.

- The report now says which rows depend on who is signed in. Reusing the person's own signed-in browser is the design -- it is how a source is read without simulating a login -- and the cost is that the list it returns is not the list anyone else would get: a live round came back from irishjobs.ie with `searchOrigin=membersarea`, and LinkedIn and Indeed were signed in too. Unsaid, two runs that saw different lists for that reason look like a change in the market. Every browser task now carries `reproducibility: session_dependent`, a row found through the browser route carries `session_dependent`, the card and the detail pane label it, and the header counts them: "three of these came from your signed-in browser" is the sentence that stops a shorter list next week from reading as fewer jobs. One such route among several is enough, since the question is whether this row's visibility depended on the session. An ATS API and a Web Search return the same thing to anyone and are not marked -- marking those too would make the label mean nothing.

- A source whose listings live on another host can now say so, and publicjobs.ie does. It serves its own front page and serves every vacancy from `publicjobs.tal.net`, so the browser boundary -- derived from the entry URL's host -- refused the only page with jobs on it, and the live round on 2026-09-25 failed that task with `host_boundary`. `listing_hosts` on the seed joins the task's `allowed_hosts`, so the widening is recorded in the catalog and visible in the plan rather than decided by whoever is browsing; a host nobody declared is still out of bounds, and the ATS handoff list still widens what a redirect means rather than what may be browsed. Validated as a bare lowercase hostname, because anything looser would let a seed open a whole URL space by writing a path into it, and a host that merely repeats the entry host is refused as a widening that widens nothing.

- A site that writes down its own pace is now heard. `check_robots.py` reports `Crawl-delay`, seeds carry `min_interval_ms`, and `browser_control.py` reads the catalog and uses whichever is slower -- the global floor or what the source asked for. `publicjobs.tal.net` publishes `Crawl-delay: 10`, twice the five-second floor, so every read of it until now was at double the rate it requested in writing. Read from the catalog rather than passed in by the caller, because a pace the executor has to remember to apply is one that gets forgotten on the run where it matters; a catalog that will not load falls back to the floor rather than stopping the action being recorded. Only ever slower: a seed cannot ask to be read faster than everything else. A site that says nothing about pace returns `None`, not a default, since an invented delay is indistinguishable from one the site actually asked for.

- That host also closes everything to `ClaudeBot` and `GPTBot` by name while leaving `*` open. Reading the named group as ours would disable a public-sector portal nobody closed to us, and reading ours as theirs would be the same mistake pointed the other way -- so the `*` group governs, and the operator's stance is recorded on the seed as `operator_blocks_named_ai_crawlers` for a person to weigh rather than left unsaid.

- Amazon's Irish listings are fetched as JSON instead of browsed. `search.json` filtered by country and asked for no query behaves exactly like a board: measured 2026-09-26, three requests and 1.5 seconds returned all 208 Irish postings, every one carrying its full description, 32 fields each, nothing dropped. The browser route reads the same postings a page of twenty-five at a time with a five-second interval between actions. No `base_query` is sent -- a board is fetched whole and filtered locally, which is what makes its result reproducible and its query-writing unnecessary, and sending search terms to this one endpoint would give it a different and unrepeatable basis from every other source; the country code is which listing to read, not a search term. `amazon-careers` keeps `web_search` and `manual_browser` and gives up `public_read_only_page`, so the same employer is not also browsed.

- `public_read_only_endpoint` stopped being an access method the catalog accepted and no seed could use. `ats_view_from_registry` selected on `source_type == "ats_board"`, so the structured channel only ever meant ATS boards however a seed described itself; it now selects on having a fetchable provider and a board token. `ATS_API_PROVIDERS` and `STRUCTURED_PROVIDERS` are now two sets rather than one, because they answer two questions -- being fetchable is not a claim to have an ATS API, and collapsing them would let a seed declare `ats_public_api` for a provider that has none. Writing fetch health back no longer rebuilds a whole record from the board view either: that would have relabelled a seeded `company_careers` endpoint as an `ats_board` with access methods it does not have, so only the health fields move and a new record is built only for a newly discovered board, which is always one of the three ATS providers.

Every invocation resolved its metrics file, round budget and source pacing state from the skill's own `data/`, so a single rehearsal call landed in the production metrics store and the production pacing state, where it is indistinguishable afterwards from a real round -- this session put a false `browser_paced_too_fast` event into the live metrics exactly that way, and had to hand-restore a pacing timestamp a test had overwritten. `--data-dir` moves all three together; redirecting only the metrics would have left the other two writing live, which is the same failure one notice quieter. Two of the three paths were also bound as default arguments and therefore frozen at import, the defect already found and fixed in `SourcePace`: `BrowserRoundBudget` and `BrowserController` now resolve theirs on construction, and one parametrised test pins all three rather than the one that happened to be caught. A test also covers the read side -- a rehearsal asked how long to wait answers from its own sandbox, not from what the live round touched.

- A browser action whose moment was never captured had no way to say so. `--occurred-at-ms` accepted an exact time or nothing, and nothing meant now -- so one untimed action in a batch reported afterwards claimed to have happened after the actions that really came later, and pacing judged the whole batch on a timeline that never existed. It produced a false `browser_paced_too_fast` in a live round on 2026-09-25, from an ordering mistake that the caller had no correct way to avoid. `--timing unavailable` is the missing third answer, the same shape `timing` already had for a Web Search page run without a clock around the call: the action happened, it was not timed, and nothing is invented to fill the gap. Such an action is not paced and -- equally important -- does not move the source's stored timestamp, because recording a guess would make every later action be measured from a moment nobody observed. It still counts as browser coverage: the page really was fetched, only the stopwatch is missing. It cannot be combined with `--occurred-at-ms`, since half a stopwatch is not a measurement and a caller should not be able to pass a number and disclaim it in the same breath. Because an untimed action is exempt from pacing, `metrics.browsers.untimed` counts them, for the reason `search_pages_untimed` exists: an exemption nobody can see is an exemption nobody audits.

- A browser route that stopped counted as a browser route that ran. `assess_run_completeness` took every event with `ok=True` as evidence the operation happened, and `user_action_required`, `rate_limited` and `resumed` are all written with `ok=True` -- correctly, because stopping at a login wall or backing off a 429 is the route behaving well, not a fault. The effect was that a round whose every browser task hit a login wall reported `complete: True`, and WORKFLOW's promise that a failure report cannot make a broken route look instrumented held only for the routes that broke loudly. Panel state reports had the same hole: `record_state` writes `action=state` to drive the local browser panel, and announcing a state satisfied the gate. Completeness now counts an event only when it reports work -- not a failure, not a lifecycle status, not a state report -- while those events keep their `ok` and stay out of the failure counts, because none of them is a malfunction. `resumed` is in the lifecycle set because it comes only from `HandoffWindow.status_at`, whose one other answer, `timeout`, was already a failure: it says the wait ended, not that anything was fetched. A test pins the full action-status vocabulary against the two sets, so a newly added status has to be placed on one side rather than silently counting as work.

- Pacing counted actions while the site counted requests, and the two differ by an order of magnitude. `browser_min_source_interval_ms` spaces one action from the next, but one card click on an Indeed result page was measured at 14 requests, so five seconds between actions is about 2.8 requests a second rather than the 0.2 the setting reads like -- and nothing anywhere enforced the number a site's own rate limiter actually watches. The request count is now a quantity in its own right: `action --requests N` and `pace --requests N` take what the caller measured in the page (the difference between two same-origin `performance.getEntriesByType('resource')` counts), `SourcePace` keeps a trailing 60-second window of it per source, and `browser_max_requests_per_minute` (default 120, lowerable only) is the ceiling. An action reported without a count is charged `browser_assumed_requests_per_action` (default 10, raisable only), because one is the only count that is certainly wrong. The three defaults are set so the two limits bind at the same moment -- 120 / 10 is 12 actions a minute, which is one every 5000ms -- so an existing caller is paced exactly as before and measuring can only make the answer more accurate: a cheap action stops paying for a page load it never made, and an expensive one stops being free. Going over is written as `failure_kind=browser_request_budget_exceeded` and kept out of the round's completeness, named apart from `browser_paced_too_fast` because every action that trips it kept its interval. `pace` answers with whichever limit binds later, so waiting the advised time is still always sufficient. The stored pace file gains a window alongside the timestamp and still reads the old bare-timestamp form; the window starts empty after the upgrade, which undercounts for at most one minute and invents nothing.

- Link verification read every HTTP error as a closed posting, so a site that refuses bots looked exactly like a site whose job had been taken down. `if code >= 400: alive = False` grouped 403, 429 and 5xx with 404 and 410, while the script's own docstring reserved `null` for the undetermined case. The two mistakes do not cost the same: WORKFLOW removes a job that verifies dead, so reading a refusal as a closure deletes a real posting, whereas reading it as undetermined only forgoes one piece of evidence. It also fell hardest on exactly the wrong channel -- the browser route exists for sites that refuse a plain HTTP client, so its output is the most likely to be refused and the most likely to be thrown away. Caught while verifying a finished round on 2026-09-25: irishjobs.ie answered this script's user agent with 403 and the posting was reported dead, while the same URL opened in a browser with its title intact and no closure wording anywhere. Only 404 and 410 now mean gone; every other status at or above 400 returns `null`, and confirming one of those is the browser layer's job. A test pins the gone-code set so widening it has to be deliberate. The script previously had no tests at all; it now has fourteen, covering both codes that remove a job, six that must not, body-keyword closure, a redirect that drops the job id, transport failures, and the CLI continuing past one bad URL.

- Pacing waited before actions that never reach the site, which was almost the whole cost of reading a page. `read` and `snapshot` operate on the already-loaded document, and the interval was applied to them exactly as to a request. Measured on a live result page on 2026-09-25 by counting the origin's entries in `performance.getEntriesByType('resource')`: four observations back to back issued 0 requests in 102ms, an idle page issued 0 over four seconds, and one card click issued 14. Pacing an observation therefore bought the site nothing and cost a full interval each time -- across a 25-job page, 95% of the elapsed time was this wait. `create`, `navigate`, `act` and `extract` are paced; `read`, `snapshot`, `wait` and `close` are not, and just as importantly they no longer advance the stored timestamp, which would have made the next real request wait out an interval measured from something that sent nothing. `extract` is paced with the network actions because its name does not say where its data comes from, and pacing something local is only slow while not pacing something remote is rude. `pace --source-id S --action A` answers for a specific action and returns zero for an observation, and the result of `record_action` now says whether pacing applied at all. A test pins the split against the full action vocabulary, so a newly added action has to be placed on one side deliberately rather than defaulting to unpaced. Separately, the interval is still counted in actions rather than requests, and one click was measured at fourteen of them -- so the floor is about an order of magnitude looser than its name suggests, which is recorded rather than fixed here.
- `SourcePace` bound its default path as a default argument, so it was fixed at import and redirecting `DEFAULT_PACE_PATH` redirected nothing. The test added with the pacing fix believed it was writing to a temporary directory and was in fact reading and overwriting this repository's own `data/browser_source_pace.json`, which made the suite depend on live pacing state and corrupt it: run twice in a row it failed the second time, because the first run had left a timestamp newer than the times the second one reported. The path is resolved on construction, and a test pins that redirecting it works.

- The two-key acknowledgement that lets a guarded source be reached never reached the browser channel, so the feature could not do the thing it was added for. `source_registry.build_source_plan` honoured `risk_acknowledged_sources` and admitted the source to the plan, and then `discovery_plan.py` -- which had never read `risk_accepted_sources` at all -- dropped it again on `automation_allowed is not True`. That test can never pass for a guarded source, because `source_registry` refuses a seed that claims both `requires_risk_ack: true` and `automation_allowed: true`; the acknowledgement was therefore inert by construction, and the only visible symptom was a source that cleared `risk_not_acknowledged` and then reappeared under `excluded.browser_policy`. Found by acknowledging both guarded sources on 2026-09-25 and watching the plan build four browser tasks, none of them theirs. The channel now honours an acknowledgement, and only an acknowledgement the catalog agrees with: being named locally is not enough, the seed must carry `requires_risk_ack` too, so a stale local name cannot open a source nobody gated. The `public_read_only_page` requirement is not waived by an acknowledgement -- `jobs-ie` stays refused for a reason the acknowledgement has nothing to say about. Each browser task now states its own `requires_risk_ack` alongside the source's `constraints`, so whoever executes a wave can see which tasks are there on an override rather than by default. The catalog check itself is unreachable through the public path, since seed validation forbids the shape that would exercise it; a test pins that invariant instead, and fails first if it is ever loosened.

- Browser pacing judged an action by when it was reported rather than by when it happened, so a properly paced run was refused and an impatient one would have passed. Caught in a live round on 2026-09-25: two actions genuinely 5.2s apart at the browser were reported 0.11s apart, and the second was written as `browser_paced_too_fast`. The reverse is the worse half -- a caller that hammered a site and reported slowly satisfied the gate -- and neither needs bad faith, only an Agent that performs a sequence and reports it afterwards, which is the normal shape of this work. `record_action` now takes `occurred_at` (`--occurred-at-ms` on the CLI, defaulting to now so every existing caller keeps its meaning) and the gap is measured between actions. A report arriving out of order yields a negative gap, which measures nothing and is refused rather than quietly accepted; the stored time never moves backwards.

### Added

- A source whose operator forbids automated access can now be reached, but only behind two keys that cannot both live in this repository. LinkedIn's robots.txt ends `User-agent: * / Disallow: /` and its User Agreement forbids "browser plugins and add-ons or any other technology" used to scrape the Services; Indeed's terms name "bots, scrapers, spiders, AI or Agentic AI" outright and disallow `/viewjob`, so a posting's own page is off limits even where the result list is not. Both are recorded in `source_seeds.json` as `automation_allowed: false` with `requires_risk_ack: true` and a `constraints` list naming why, and a test refuses a guarded source that states no reason. Such a source is planned only when its `source_id` also appears in `risk_acknowledged_sources` in the person's own `data/browser_provider.json` -- a directory this repository ignores, so a clone plans none of them and no commit here can open one in someone else's checkout. The plan reports `risk_accepted_sources` for the wave to show before it runs, and `excluded.risk_not_acknowledged` for the ones it left out. The flag is an override of a refusal and nothing else: declaring it on a source that permits automation is rejected, and the existing rule that `automation_allowed: false` cannot declare a direct access method still holds everywhere the flag is absent. The four standing prohibitions are outside the exception and unchanged -- no CAPTCHA bypass, no simulated login, no identity or IP masking, no detection evasion -- which is also what the operators' own crawling terms forbid, and what separates reading an authorised session from circumventing a control. These two sources cannot be verified the way every other entry is, because each of this repository's verification methods fetches the source and fetching is the thing they forbid; they carry `operator_terms_reviewed`, which is the only check that was actually performed.
- Browser actions are now paced per source, for every source rather than only the guarded ones. `browser_min_source_interval_ms` (default 5000, raisable but floored -- a limit that could be set to zero would be a suggestion) spaces two actions against one `source_id`; `browser_control.py pace --source-id S` reports what is left to wait, and `action --source-id S` enforces it. Nothing in this process can actually hold the Agent back, since it drives the browser through its own runtime, so an action that arrives too soon is still written -- staying visible -- but as `failure_kind=browser_paced_too_fast`, which keeps it out of the round's completeness. Pacing is per source because it is courtesy to the site being read, and two sites are not each other's traffic; an action reported without a `source_id` keeps exactly the meaning it had before. `browser_jitter_ms` (default 2000) adds a random wait on top of that interval and never takes one off it, so the enforced floor stays deterministic and the advised wait is always sufficient. It exists to spread requests out for the site being read, not to disguise them: bot detection reads TLS and browser fingerprints rather than the spacing between two page loads, and no part of this tries to defeat a classifier -- the prohibition on detection evasion is unchanged.
- A Web Search page can now report that it could not be timed, instead of being forced to invent a latency. `pages` required `duration_ms` on every page, and the executor it required it from is the Agent, which runs Web Search through a tool call it has no clock around: the tool returns titles and URLs and no timing, and bracketing the call with two shell timestamps measures the turn, not the search -- 11.6s on 2026-09-24 for a search that takes one to three. That left two exits, both dishonest: put a plausible number in the store, or report the whole task `skipped` and throw away candidates it really did find. A page may now declare `"timing": "unavailable"` and set `duration_ms` and `first_result_ms` to an explicit `null`; they go absent together, because half a stopwatch is not a measurement, and the key must still be present, because an omission reads the same whether it was meant or forgotten. The default is `"measured"`, so every page written before this keeps meaning what it meant. Two things stop it becoming a way out of the instrumentation it was added to protect: **the counts do not soften with it** -- `raw_results` and the rest are things the Agent can actually count, so the funnel and the per-task sums are still enforced -- and **the declaration is recorded rather than absorbed**, on the event as `timing`, on the batch result as `search_pages_untimed`, and in the rollup as `search.duration_ms.reported_rate`, which is what stops a round that timed nothing from looking exactly like a round that searched nothing, both being a null p50. Nothing here can tell an executor that cannot measure from one that did not bother; the point is only that it is no longer *made* to choose between two lies. `duration_ms` is nullable for `search` alone -- everywhere else the caller times its own work, and a null would only mean it forgot, which must stay indistinguishable from absence rather than become a legal value. The path #43 built was verified end to end for the first time on 2026-09-24: two real Dublin searches and eleven ATS boards committed as one wave, 13 of 13 tasks succeeded, 1,920 jobs fetched, 7 candidates merged, both pages recorded as untimed, and `reported_rate` fell to 0.6 across the store -- three older `search` events carry latencies because they came from the separate `search_metrics.py` call this contract replaced, and those are the events that used to be missing entirely.
- The city catalog lost postings that named a city without its country. `references/markets.json` listed Berlin, Munich, Hamburg, Frankfurt and Cologne but not Dusseldorf, Stuttgart or Hanover, and a city it does not list resolves to no market at all -- silently, because an unmatched location is indistinguishable from one in a market nobody targets. It cost a whole board: trivago posts every job in Dusseldorf, so the 2026-09-23 catalog build rejected it as having no target-market work. Measured across 6,532 real postings, only three were lost this way (`Hannover` twice, `Dusseldorf` once) because almost every posting names its country too and resolves at country level regardless; the ones carrying a bare city name are exactly the ones a gap drops. Six German and three UK cities were added, which also lifts 70 `Bristol, UK` postings from country to city precision, and trivago joins the ATS catalog as its 49th board. Cambridge, Birmingham and Oxford were deliberately left out: no market here models the United States, so nothing would contest a UK alias and `Cambridge, MA` would resolve as Cambridge, England -- the same confident wrong answer in the other direction. A test pins that they stay unresolved, and another pins that no city name is claimed by two cities. Region names are shared on purpose -- `England` names both London and Manchester -- so the new cities declare no administrative areas rather than make `Nordrhein-Westfalen` mean Cologne or Dusseldorf by catalog order.
- Remote job support was removed rather than repaired, and a round no longer searches remote work at all. `references/markets.json` carried a `remote_scopes` catalog that `normalize_location` read a location label against, and a qualifier the catalog did not list fell through to `global` -- worldwide. `Remote - US`, `Remote - India`, `Remote - Spain` and a bare `Remote` therefore all resolved identically, to the one answer that is wrong for three of them: the module could not tell "open anywhere" from "open somewhere else", while claiming it could, in a function whose own docstring is `without guessing unknown places`. Extending the catalog does not fix it. Of 422 real remote-labelled postings sampled on 2026-09-23, 51% state their hiring restriction only in the description -- `must reside in, and perform all work exclusively from within, the United States`, `based in Colorado, Hawaii, Illinois, Maryland`, `based in the UK, Ireland, Germany, the Netherlands` -- at a granularity finer than country, because the binding constraint is where an employer has an entity, an EOR or the appetite for permanent-establishment risk, not where the company sits. The deciding text lives in the job description, which by design never reaches the orchestrator, so searching remote honestly means changing the data flow rather than adding aliases. `open_to_remote` is gone from the CV profile and the prefilter, the scope catalog and its resolution are gone from `market_plan`, and a location naming remote is skipped whatever else it names. `location_normalized.remote_scope` stays in the CandidateEnvelope, always null: the contract and the 24 stored jobs keep their shape, and nothing claims a jurisdiction any more. `docs/roadmap.md` is new and records what doing this properly would require and how it would be judged done.

The structured channel is the only one producing jobs, so the pool it draws from was the ceiling on the whole 2026-09-23 run: 20 jobs reached the report and one of them scored an `apply`. 155 candidate tokens were probed by the existing rule -- no token trusted because it looks right, each fetched through this repository's own read-only adapter, markets taken from the locations a board's own jobs report rather than from where the company is headquartered -- and the 18 existing boards were revalidated first, which is what proves the probe works. 40 probes reached a live board and 30 were kept; 115 tokens had no board behind them, which is the expected cost of guessing one and spending one request to find out. - Every CLI here reads stdin to end-of-file, and end-of-file arrives only when the writer closes the pipe. Started from a background shell that keeps its end open, a script waits on that read forever: no output, no progress, no timeout, and nothing to tell it apart from slow work. `ats_pipeline.py run` did exactly that on 2026-09-23 and was left running for nine hours before anyone doubted it, which is the expensive half of the failure -- the hang itself cost minutes, not knowing cost the day. `_stdio.read_stdin_text()` bounds the wait at 30 seconds (`JOB_MATCHER_STDIN_TIMEOUT`, 0 to restore the unbounded read) and every one of the eighteen scripts that read stdin now goes through it, reporting `{"ok": false, "error": ...}` on stdout like any other input failure rather than a traceback a caller cannot parse. A terminal is exempt: end-of-file is one keystroke away there and the person can interrupt. Tests pin the failure itself against a real pipe whose writer never closes, and a per-script scan refuses a direct `sys.stdin.read()` so a new entry point cannot reintroduce it.
- `market_plan.normalize_location()` no longer lets a city lose to a country whose name happens to be longer. The winning match was chosen by alias length before specificity, so which reading survived depended on spelling rather than geography: "Frankfurt, Germany" kept its city, "Dublin, Ireland" did not. - `update` now requires `--run-id` and accepts only evaluation-owned fields associated with that run.
- Corrupt canonical JSON now fails closed instead of being treated as an empty table.

### Security

- Evaluation manifests exclude the raw CV and avoid copying the complete canonical job table.
- Search-owned fields cannot be overwritten by evaluation output.
- Out-of-range scores and malformed evaluation results are rejected before persistence.

### Breaking

- Direct callers of `scripts/merge_jobs.py update` must pass the `run_id` returned by the corresponding `merge` call.
- Evaluation workers must echo `dedup_key`, `base_record_version`, and `jd_input_hash` from their assigned task.
- Legacy evaluation results without run-scoped snapshot metadata are rejected.
