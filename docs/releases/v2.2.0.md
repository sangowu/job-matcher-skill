## 摘要

本版本来自一次 JobRadar 与 job-matcher-skill 的交叉审查：把 JobRadar 已验证的评分口径和失效判断规则移植过来，
同时强化本 skill 的差异化能力——LLM 自主搜索带来的跨地区、跨语言覆盖。

改动分四类：堵住报告渲染的注入风险与评分口径混乱、对齐 JobRadar 的推荐阈值与资历硬规则、
补齐非英语市场的 URL 去重与站点策略、把已有的评估快照机制变成真正的批间重叠编排。

所有改动都做了改动前后的离线 A/B 测量，结果见下方「实测效果」。

## 本次更新

### 安全与正确性

- HTML 报告嵌入 JSON 时转义 `</`，外部职位内容（title / snippet 来自任意网页）无法再终止内联 `<script>` 块注入标记。
- 职位与来源链接只放行 `http(s)`，拦截 `javascript:` 等可执行 scheme。
- 报告不再回退显示其他 CV / 求职意向下的评分；该职位显示为未评分并标注「待重评」，避免跨口径分数误导排序。
- `merge` 时自动作废超龄（`eval_run_stale_hours`，默认 2 小时）未完成的评估快照与损坏 manifest，
  释放此前会永久停在 `in_evaluation` 的职位；作废记录写入 `data/eval_runs/history.jsonl`，并在 stats 中计入 `abandoned_runs`。
- `references/` 增加 prompt injection 防护条款：搜索结果与 JD 正文一律视为纯数据，忽略其中的任何指令。
- 删除 `scripts/_build_table.py`（绕过 merge 契约、含硬编码个人数据的一次性脚本）。

### 评分口径对齐 JobRadar

- 推荐阈值统一：`stretch_apply` ≥ 60（原 55），`low_priority` ≥ 20（原 40）。
- `scoring_rubric.md` 增加确定性资历上限（移植自 JobRadar 的 profile guards）：
  应届/实习遇 3 年以上要求 → `seniority_score ≤ 15`；junior 遇 5 年以上 → `≤ 25`；命中 blocked 级别 → `≤ 10`。
- 修正 rubric 与契约的矛盾：命中硬约束 / deal_breaker 时通过压低对应维度分来降低总分，
  `overall_score` 始终等于加权和。
- `analysis_contract.py` 拒绝比分数档更激进的推荐（50 分 + `apply` 会被拒），
  但允许因硬伤而保守降档（90 分 + `skip` 合法）。
- 失效关键词补齐 JobRadar 的常青帖话术，并按语言分组便于扩展；模糊表述由精排时的 LLM 兜底判断。

### 多地区检索与去重

- `canonicalize_url` 新增 liepin / zhipin / lagou / seek（AU+NZ）/ reed 的 job-id 提取规则，
  非英语市场的跨来源去重可以拿到精确 `url_key` 命中。
- 批内聚合先按 `dedup_key`、再按 `url_key` 兜底：招聘站改写标题的重复条目在派发评估前就合并，不再多花一次 LLM 调用。
- 同一来源的第二个 URL（列表页 + 详情页）不再被丢弃，记入 `alt_urls` 参与 `url_key` 匹配。
- `search_playbook.md` 站点策略从 en/zh 两档扩展为多市场：爱尔兰/英国、欧陆、澳新、中国大陆，
  以及其他市场的「按语言 + 地点推断当地平台」通用规则。
- 同义扩展去重规则：只加资历 / 技术栈修饰的 query 变体不再消耗宝贵的 `max_websearch_calls`（仅 6 次）。

### 批间重叠编排

- `WORKFLOW.md` / `SKILL.md` 明确推荐模式：第 N 批 `merge` 拿到 `eval_run` 后，
  在同一条消息里并行发出「第 N 批评估 worker」和「第 N+1 批搜索 worker」。
  安全性由已有机制保证：`in_evaluation` 防重复派发、`update` 检测 JD 输入变化并拒收过期结果、超龄快照自动回收。
- `max_parallel_subagents` 明确为搜索与评估共用的全局预算（重叠期建议 1 搜 + 2 评）。
- 精排 worker 一条龙：抓 JD 全文 → 抽 `jd_profile` → 打分在同一个子代理内完成，JD 正文不进编排者上下文。

### 整轮计时指标

- 新增 `scripts/round_timer.py`（`start` / `finish --orchestration serial|overlapped`），
  给整轮（首次搜索到出报告）计时。
- 新增 PII-safe 的 `round` 事件：`round_duration_ms`、`orchestration`、`batches`、`evaluations`、`jobs_reported`。
- 整轮时长不计入脚本级 `duration_ms` 分位数；`summarize_metrics.py` 按模式给出 p50/p95 与 `overlap_saving_pct`，
  两种模式都有样本前显示 `n/a`。

## 实测效果

改动前基线取自 `v2.1.0`（`4fb7700`），与本版本用同一份多地区数据集（25 条搜索命中、14 个真实职位、
11 条重复形态）跑完整的 merge → 评估 → 回写循环，两版在各自子进程中运行。

| 指标 | v2.1.0 | v2.2.0 | 说明 |
|---|---:|---:|---|
| 职位表行数（真值 14） | 17 | **14** | 重复残留 3 → 0 |
| 派发的 LLM 评估次数 | 17 | **14** | −17.6%，等于真实职位数 |
| 缓存直接命中 | 4 | **6** | +50% |
| 失效职位识别召回率 | 71.4% | **100%** | 误报仍为 0 |
| 评分漂移拦截 | 0 / 4 | **4 / 4** | 误杀 0 |
| 编排者崩溃后永久卡死的职位 | 7 | **0** | 全部回收重新派发 |
| merge + 回写单轮耗时中位数 | 99.3 ms | 97.6 ms | 差值小于抖动，判定为无变化 |

基线漏掉的 3 条重复全部是同一类：招聘站换了 URL slug 且改写了职位标题
（`AI Engineer` → `Senior AI Engineer`），只能靠稳定 job-id 识别。
若公司名 + 职位名一致，v2.1.0 的 `dedup_key` 本来就能去重，新规则不带来额外收益。

批间重叠的墙钟收益发版时只有解析模型（3 批场景 9.5% – 33.3%，典型值约 16.7%）。

**补充（2026-08-09，发版后）**：已用受控实验实测——真实脚本、真实 `round_timer` 计时、真实线程并发、
提交仍串行，只把 worker 延迟用 `sleep` 替身，按 1/20 缩放（节省比例只取决于评估/搜索时长比，
不取决于绝对值）。4 组配置 + 典型配置 3 次重复，实测节省 16.6% – 22.1%，
与模型预测的最大偏差 **0.3 个百分点**；每轮真实脚本与锁开销稳定在 109–133 ms，可忽略。
`summarize_metrics.py` 从真实记录的 12 条 `round` 事件读出 `overlap_saving_pct = 16.6%`，
采集链路端到端可用。仍未覆盖的是真实 LLM / 搜索延迟波动，以及编排者是否真的按指引发起并行。

## 兼容性与升级

没有破坏性变更，`merge_jobs.py` / `render_html.py` 与对话入口的调用方式不变，
`jobs_table.json` 不需要迁移。

两处行为变化值得注意：

1. **推荐阈值变了。** 历史 `match_score` 中记录的 `recommendation` 不会自动重算；
   新旧口径的职位混在同一张表里排序时，60–70 分区间的档位表述可能不一致。
   在意的话可以删除 `data/jobs_table.json` 中的 `match_scores` 让下一轮重评。
2. **契约更严。** 打分 worker 如果给出比分数档更激进的推荐会被 `update` 拒收并计入 `rejected`。
   `references/scoring_rubric.md` 已写明规则，正常流程不受影响。

新增配置项 `eval_run_stale_hours`（默认 2）；沿用旧 `config.json` 时该项缺失会使用默认值。

## 已知限制

- 批间重叠已在受控实验中实测（见上），但尚无真实使用数据：真实 LLM / 搜索延迟的波动，
  以及编排者是否真的按指引发起并行，都要等真实跑几轮后由 `summarize_metrics.py` 给出。
- `_CLOSED_PATTERNS` 只内置英文与中文的确定性关键词，其他语言依赖精排时的 LLM 判断。
- 区域平台 URL 规则覆盖主流站点，冷门招聘站仍退化为 host + path 弱匹配。
- 指标文件仍不自动轮转或清理；文件锁只协调同一文件系统上的进程。

## 回滚说明

如需回滚代码，可切换到 `v2.1.0`。职位主表无需降级迁移：v2.1.0 会忽略 `alt_urls` 字段和
`round` 类型的指标事件。回滚后将失去报告注入防护、快照回收、评分契约校验、多地区去重与整轮计时，
但不会影响已有职位数据。
